Current Architecture

Step 1

Instrument Files

Each monitor writes data on the field laptop. The uploader discovers files using configured glob patterns.

Step 2

Uploader Script

scripts/upload_instrument_data.py reads only new complete lines, uses checkpoints, and buffers failed uploads in SQLite.

Step 3

S3 Bronze

Raw batches are uploaded to {instrument}/bronze/year=YYYY/month=MM/. This keeps original data traceable.

Step 4

S3 Silver

aq-silver-builder filters real rows, removes duplicates, and writes one clean CSV plus metadata per instrument.

Step 5

Dashboard API

API Gateway calls aq-dashboard-api. The dashboard reads metrics and can browse Silver records after deployment.

What Is Live Now

  • Bronze upload is working. The laptop pipeline uploads new data to S3 and tracks per-file offsets.
  • Silver records exist in AWS. All five instruments have Silver CSV and metadata objects.
  • Dashboard metrics are served from AWS. The live API URL is https://yvhb48sthk.execute-api.us-west-2.amazonaws.com/metrics.
  • Vercel dashboard is live. It reads the configured API URL from VITE_API_URL.

What Is Ready In Code

  • Data Review page. The dashboard has an Overview tab and a Data Review tab.
  • Time window browsing. Operators can select instrument, start time, and end time to load Silver records.
  • Flag selected rows or full time range. Flags will be stored in S3 under {instrument}/flags/.
  • Correction notes. One selected row can be edited, and the correction is stored as JSON under {instrument}/corrections/.

Why This Design Is Enough Now

  • We only know the wrong time period, so browsing by time range is more practical than asking for exact record IDs.
  • Bronze remains untouched. Flags and corrections are sidecar JSON records, so original instrument data is preserved.
  • Silver CSV is simple and low cost for current volume. Delta Lake or Iceberg is not required yet.
  • We can add Iceberg later if we need table transactions, many editors, SQL updates, or long audit history at large scale.
